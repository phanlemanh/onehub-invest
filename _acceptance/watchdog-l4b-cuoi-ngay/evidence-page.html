Vì sao làm

ZC3 (audit-p1-resilience, đã merge) sửa lớp L4b của watchdog để không sót agent-turn ở đầu file log ngày mới. Phiên kiểm của ZC3 ghi một lỗ ngoài hợp đồng: dòng ghi vào CUỐI file hôm qua SAU lượt quét cuối ngày (khoảng 23:55–00:00) không bao giờ được quét. Lý do là lượt sau đã đổi sang file ngày mới. Một agent-turn rơi vào 5 phút cuối ngày vì thế lọt lớp canh an toàn Zalo.

Đã hứa
  1. AC-1 — Given lượt quét cuối ngày đã ghi marker cho file hôm qua, và sau đó một agent-turn được ghi vào dòng cuối file hôm qua, When lượt quét đầu ngày mới chạy trên file hôm nay, Then:
  2. AC-2 — Given file hôm nay có agent-turn ở dòng 1, When lượt quét đầu ngày mới chạy, Then turn đó được bắt, và toàn bộ file hôm nay được quét.
  3. AC-3 — Given đã quét xong (kể cả đuôi file cũ), When chạy lại không có dòng mới hoặc chỉ nối thêm vào file hôm nay, Then không in gì, hoặc chỉ in phần mới; dòng của file cũ không bị báo lại.
  4. AC-4 — Given file cũ đã bị xoá, hoặc đường dẫn cũ bị tái dùng bởi một file khác (inode khác), When lượt quét đổi sang file mới, Then không lỗi và không quét nhầm file lạ; chỉ file mới được quét.
  5. AC-5 — Given cùng một file bị truncate (cùng inode, ít dòng hơn), When quét, Then quét lại từ dòng 1; marker số cũ (`4211`) vẫn quét toàn file hôm nay mà không lỗi; các ca L4b/gateway của ZC3 không hồi quy.

Eval không phân biệt (Analyst)

Không có eval ui-check, nên không áp «Network truth» (`network_observed` không dùng). Baseline: chép harness mới sang thư mục tạm NGOÀI repo, dựng bằng `git archive e109402~1`, không tạo worktree. Watchdog ở đó trùng `git show e109402~1:scripts/zalo-watchdog.sh`. Chạy xong đã gỡ. - E1 đỏ trên baseline: mục (a) không bắt turn, chỉ in 2 dòng. - E2 đỏ trên baseline: lượt đầu ngày mới thoát sạch, không KILL, không gọi stub. Hai eval này phân biệt code mới với code cũ. Eval không phân biệt (xanh trên cả hai cây, xét đúng mục con mà eval trích): - E3, E4, E5, E6: lệnh `scan` chung đỏ trên baseline chỉ vì mục (a). Các mục con (b), (c), (d), (e)/4211/gateway mà E3–E6 trích đều xanh trên e109402~1. Đúng bản chất AC-2..AC-5, vốn là tiêu chí «giữ hành vi», nên chúng là rào hồi quy, không phải bằng chứng tính năng. - Bù cho E5: đột biến bỏ kiểm inode (`if [ "$oldInode" = "$prevInode" ]` → `if true`) làm đỏ mục (d) should-NOT-fire và mục marker 4211. Như vậy E5 bắt được một bản cài sai hợp lý. - E7, E8, E9: rào hồi quy ZC3 có chủ đích (harness ZC3 không đổi từ e109402~1). Xanh trên cả hai cây là đúng kỳ vọng.

Giới hạn và ngoài hợp đồng
  • Chạy watchdog thật lên OpenClaw, đụng `~/.openclaw`, `/tmp/openclaw` thật, `launchctl`: alert() kill gateway (luật 8).
  • gateway.log xoay kiểu đổi tên (`gateway.log` → `gateway.log.1` rồi tạo file mới cùng đường dẫn): phần đuôi của file đã đổi tên không được quét nốt, vì cùng đường dẫn nhưng inode khác thì code coi là file lạ.
  • Lần chạy thật đầu tiên sau triển khai — do ZCode làm qua kênh tin.
  • Mọi bằng chứng là sandbox: hàm trích nguyên văn, hoặc bản chép đổi 2 dòng với stub. Chưa có lần chạy thật nào sau triển khai; việc đó do ZCode làm qua kênh tin, theo Out of scope.
  • Đuôi file cũ có turn mà file cũ đã bị xoá trước lượt quét đầu ngày mới: turn đó mất. Hợp đồng chọn thế (AC-4, bỏ qua im lặng), phép thử P3 xác nhận. Chấp nhận được khi /tmp chỉ bị dọn file vài ngày tuổi, không dọn trong 5 phút quanh nửa đêm. Lịch dọn /tmp thật của máy chưa đo.
  • Ngày mới mà /tmp chưa có file (OpenClaw im lặng): watchdog chỉ gọi `scan_new_lines` khi `[ -f "$OC_LOG_GLOB" ]` (dòng 132). Phép thử P4 cho thấy đuôi ngày cũ được quét ở lượt ĐẦU TIÊN có file ngày mới, dù cách vài ngày, miễn file cũ còn và cùng inode. Turn 23:58 vì thế có thể được phát hiện trễ tới khi file ngày sau xuất hiện. Code cũ thì không bao giờ phát hiện.
  • Chưa kiểm cách OpenClaw đặt tên file /tmp theo ngày: ngày theo thời điểm ghi, hay cố định lúc khởi động. Không đọc được `/tmp/openclaw` thật (luật 8). Nếu OpenClaw ghi tiếp vào file hôm qua sau nửa đêm, phần ghi sau nửa đêm chỉ được quét khi một file ngày mới xuất hiện.
  • gateway.log xoay kiểu đổi tên (`gateway.log` → `gateway.log.1`): turn ở đuôi file đã đổi tên không được quét. Phép thử P5 xác nhận. Đây là giới hạn đã khai ở Out of scope.
  • File cũ bị truncate (cùng inode, ít dòng hơn marker) rồi mới xoay ngày: đuôi cũ được quét từ `prevLines+1` của file ngắn hơn, nên không in gì. Phép thử P6: turn trong file cũ sau truncate bị mất. Ca hiếm.
  • `stat -f '%i'` là cú pháp BSD/macOS. Đúng với máy chạy launchd này, không chạy trên Linux.
  • E3–E6 dùng chung lệnh `scan` với E1. Mỗi eval là một lần chạy riêng, có run_id riêng, nhưng cùng một bộ kiểm.
